![Isar v4 and v3 Flutter database migration decision flow](https://pub.dev/static/img/pub-dev-icon.svg)

If a Flutter app already ships with Isar v3, do not replace the dependency with Isar v4 in the next release. The current Isar repository explicitly says v4 is not ready for production, does not support database migration, and cannot open v3 databases. This matters to apps with offline records, drafts, or cached data that cannot be recreated after an update. A new app with disposable local data can evaluate v4 separately; an installed app needs a compatibility plan first.

## Why a normal package upgrade is unsafe

There are two different changes that are easy to mix up:

| Change | What must remain compatible | Safe first action |
|---|---|---|
| Isar v3 schema change | Existing collection and field storage | Test the generated schema migration |
| Isar v3 → v4 package change | Database file format and migration support | Keep v3 in the release branch |
| Isar v3 → another store | Every record and its business meaning | Export, validate, then import |

`pub upgrade` only resolves a package graph. It does not convert a database file. Removing the old package from `pubspec.yaml`, deleting the database directory, and opening a new v4 store can make the app appear healthy on a clean install while existing users lose their local state. That is the exact test gap to avoid.

## Pick the release path from the data value

Use this decision table before changing `pubspec.yaml`:

| Local data | Recommended path | Rollback condition |
|---|---|---|
| Only a rebuildable cache | Stay on v3 for now, or clear it deliberately | The API can repopulate every record |
| User drafts or offline edits | Stay on v3 and postpone v4 | A tested export/import exists |
| Auditable or irreplaceable records | Keep v3 and design a separate store migration | Old and new builds can read a verified backup |
| New app with no released data | Prototype v4 in a separate branch | No existing v3 file needs opening |

The “cache” label is not enough. A thumbnail cache may be disposable, but an offline note waiting to sync is user data. Classify each collection by whether the server can reconstruct it and whether an interrupted migration can be retried.

## A rollback-safe staging plan

The following sequence keeps the installed release and the experimental package separate:

```text
release branch: Isar v3 ──> backup/export fixture ──> remain deployable
                              │
                              ├─> test v4 in a new app or isolated store
                              └─> test import into the chosen replacement

only after validation: release a reader/importer ──> verify counts and IDs
                       ──> mark migration complete ──> remove v3 later
```

1. Pin the current v3 constraints and commit the lockfile. Record the Isar generator version too; generated code is part of the storage boundary.
2. Create fixtures from real shapes, not just an empty database: one record, a large record, an enum at every value, an unsynced draft, and an empty collection.
3. Define an export format owned by the app, such as versioned JSON. Do not treat Isar’s internal file as a portable backup contract.
4. Validate the import before replacing anything. Compare record counts, stable IDs, required fields, enum values, and sync status.
5. Keep the old database untouched until the new store passes validation and the app can reopen it after a forced restart.

For a collection that can be rebuilt, an explicit reset may be cheaper than a migration. For user data, a reset is data loss, not a migration strategy.

## Make the compatibility check executable

Put the decision in a small release check so a dependency bump cannot silently bypass it:

```dart
enum LocalDataClass { cache, draft, userRecord }

bool canDiscardLocalStore(Iterable<LocalDataClass> collections) {
  return collections.every((kind) => kind == LocalDataClass.cache);
}

void assertMigrationReady({
  required bool hasVersionedExport,
  required bool importRoundTripPassed,
  required bool rollbackBuildStillOpensOldData,
}) {
  if (!hasVersionedExport ||
      !importRoundTripPassed ||
      !rollbackBuildStillOpensOldData) {
    throw StateError('Local database migration is not release-ready');
  }
}
```

This is a policy guard, not proof that v4 is compatible. It makes the missing evidence visible in CI or a migration checklist. The import test should run against a database fixture produced by the oldest still-supported release, then repeat after an interrupted import.

## What not to promise

Do not claim that a new Isar major will preserve data because the Dart models look identical. Model compatibility and file compatibility are separate. Do not ship a “migration” that catches an open error and calls `deleteDatabase()`. That converts a recoverable rollout problem into permanent loss.

As checked on 2026-10-29, the official Isar repository still marks v4 as unsuitable for production and says it cannot open Isar v3 databases. Until that changes and a real conversion path is documented, the practical production fix is to keep v3 for released data, isolate v4 experiments, and make export/import a deliberate release boundary.

### Short checklist

- [ ] Is every collection classified as cache, draft, or user record?
- [ ] Does the oldest supported build still open its own database?
- [ ] Is the export format versioned and independent of Isar internals?
- [ ] Have counts, IDs, enum values, and sync states been compared after import?
- [ ] Can the app roll back without deleting the old store?
