The safest choice for a Flutter client that must survive API evolution is to keep `freezed`'s discriminator explicit and add a converter at the boundary. Use generated `fromJson` alone when the server and app are released together; use an `unknown` union case when an older installed app can receive a newer event. This does not make malformed payloads valid, and it should not silently turn a required business action into a generic fallback.

## The production failure

Freezed can select a constructor from a discriminator such as `runtimeType` or `type`. That works until the server adds `refunded`, while an older app only knows `pending`, `paid`, and `failed`. The generated decoder cannot select a constructor and throws before the screen can decide whether to hide, log, or defer the event.

There is a second trap during migration: changing the discriminator key or case changes the wire contract. A Dart constructor named `paid` is not automatically the same as an API value named `PAYMENT_SETTLED`. Treat the JSON key and values as protocol data, not as an implementation detail.

| Situation | Generated union only | Boundary converter |
|---|---|---|
| All clients and server deploy together | Simple and sufficient | Extra code is unnecessary |
| Server may add variants first | Can throw on an unknown value | Keeps the payload in an `unknown` case |
| API uses a different discriminator | Configure `unionKey`/`FreezedUnionValue` | Add converter only if shape detection is needed |
| Payload is missing required fields | Still fails, which is useful | Keep failure visible; do not swallow it |

## Make the wire names explicit

The first step is to stop relying on generated constructor names. The following model uses the server's stable `type` field and preserves the exact values used by the API.

```dart
import 'package:freezed_annotation/freezed_annotation.dart';

part 'order_event.freezed.dart';
part 'order_event.g.dart';

@Freezed(unionKey: 'type')
sealed class OrderEvent with _$OrderEvent {
  @FreezedUnionValue('pending')
  const factory OrderEvent.pending({required String id}) = Pending;

  @FreezedUnionValue('paid')
  const factory OrderEvent.paid({required String id, required int cents}) = Paid;

  @FreezedUnionValue('failed')
  const factory OrderEvent.failed({required String id, String? reason}) = Failed;

  const factory OrderEvent.unknown({
    required String type,
    required Map<String, dynamic> raw,
  }) = Unknown;

  factory OrderEvent.fromJson(Map<String, dynamic> json) =>
      _$OrderEventFromJson(json);
}
```

`unknown` is not a fourth server variant generated by the default decoder. It is an application recovery state, so a converter must route unrecognized values there. Keep the raw map for diagnostics only; do not expose it directly as trusted business data.

## Intercept only the unstable boundary

Freezed's documentation supports a custom `JsonConverter` when the response does not use the generated discriminator format. The same boundary is useful when the format is known but the server can add future values.

```dart
class OrderEventConverter
    implements JsonConverter<OrderEvent, Map<String, dynamic>> {
  const OrderEventConverter();

  @override
  OrderEvent fromJson(Map<String, dynamic> json) {
    final type = json['type'];
    if (type is! String || type.isEmpty) {
      throw const FormatException('Order event type is missing');
    }

    switch (type) {
      case 'pending':
      case 'paid':
      case 'failed':
        return OrderEvent.fromJson(json);
      default:
        return OrderEvent.unknown(
          type: type,
          raw: Map<String, dynamic>.unmodifiable(json),
        );
    }
  }

  @override
  Map<String, dynamic> toJson(OrderEvent value) => switch (value) {
        Pending(:final id) => {'type': 'pending', 'id': id},
        Paid(:final id, :final cents) => {
            'type': 'paid',
            'id': id,
            'cents': cents,
          },
        Failed(:final id, :final reason) => {
            'type': 'failed',
            'id': id,
            if (reason != null) 'reason': reason,
          },
        Unknown(:final raw) => raw,
      };
}

@freezed
class OrderFeed with _$OrderFeed {
  const factory OrderFeed({
    @OrderEventConverter() required List<OrderEvent> events,
  }) = _OrderFeed;

  factory OrderFeed.fromJson(Map<String, dynamic> json) =>
      _$OrderFeedFromJson(json);
}
```

Run generation after adding or changing the annotations:

```bash
dart run build_runner build --delete-conflicting-outputs
```

The converter must call `OrderEvent.fromJson` only for values it has explicitly allowlisted. Calling it for every non-null `type` defeats the recovery path because the generated decoder will still throw on a future value.

## Test the release-order failure

A useful test does not only decode the three values known today. It decodes a future value first, then checks that malformed known data still fails.

```dart
test('keeps a future event as unknown', () {
  final feed = OrderFeed.fromJson({
    'events': [
      {'type': 'refunded', 'id': 'o-7', 'cents': 1200},
    ],
  });

  expect(feed.events.single, isA<Unknown>());
  expect((feed.events.single as Unknown).type, 'refunded');
});

test('does not hide a broken known event', () {
  expect(
    () => OrderFeed.fromJson({
      'events': [{'type': 'paid', 'id': 'o-7'}],
    }),
    throwsA(anything),
  );
});
```

The release checklist is short: pin the discriminator names in a contract fixture, test one future value, test a missing discriminator, and decide whether `unknown` is safe to display or should be ignored and logged. If the server uses a different JSON shape for each variant, replace the switch with field-based detection and keep the same explicit failure for ambiguous payloads.

The practical rule is to make known variants strict and unknown variants survivable. `unionKey` and `FreezedUnionValue` protect the wire contract; the converter protects the older client from a legitimate server expansion. They solve different parts of the migration.
